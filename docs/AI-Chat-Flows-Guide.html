Startup: from "run it" to "chats on screen"

Two separate startups: the backend process boots and prepares the database, then the browser loads the page and restores your last chat.

Why it matters: the chat model (ChatOpenAI) is deliberately not created at startup. The server boots without a key, so /health works and a missing key becomes a safe error on the first chat request instead of a crash.

The newest user message is saved before the context is loaded, so the window always ends with it. Everything in the window is the masked text: a secret was refused before it could be stored, and personal data was masked before it was saved (see the Guardrails tab). Rows outside the window stay in the database and in your UI, but the model never sees them.

Why the server, not the browser?

Before (Phase 9)

The browser sent the whole history every time. A modified client could add fake "assistant" turns or oversized history.

Now (Phase 11)

The browser sends only {content, client_message_id}. The server decides the context from rows it wrote itself, so there's nothing to forge.

Code: routers/conversations.py: _recent_context (newest 20 by id, reversed to chronological order).

Streaming: from token to pixel

The reply isn't one response. It's a long-lived HTTP response made of small text frames (Server-Sent Events). The first part follows one token across three layers. The second lets you replay how the browser reassembles frames from awkwardly split network chunks.

Stop, closed tabs, and not paying for unread tokens

Cancelling is a chain reaction from the browser to the AI provider. The partial text you saw is saved, so a refresh shows exactly what you saw.

Honest detail: tokens the provider generated before it noticed the closed connection may still be billed. Stopping bounds the cost; it doesn't make it zero.

When things go wrong, and why Retry is safe

Four failure shapes, each handled differently. The key rule: a retry re-sends the same message id, so the server can tell "this message again" from "a new message", and never duplicates or deletes the wrong thing.

The database: what is written, and when

Two tables. Click a write point to see the equivalent SQL, the code that does it, and what a page refresh would show.

Since Phase 16, messages.content never holds a secret or unmasked personal data. The guard runs before the first insert, and the masked text is what gets stored (for messages, replies and uploads alike).
Order

Message order is the autoincrement id. "Last 20" and "after this message" are both id comparisons.

Idempotency

The unique pair (conversation_id, client_id) means the same user message can't be stored twice, even with concurrent retries.

Two layers of cascade

The ORM relationship deletes messages on db.delete(conversation); the foreign key (with PRAGMA foreign_keys=ON) guarantees it at the database level too.

Sessions: why the stream opens its own

A request's database session (the get_db dependency) is opened when the request starts and closed with it. The assistant reply is saved at the end of a long stream, possibly after the request's session is gone, and also when the client disconnects. So _save_assistant_message opens a fresh session (database.SessionLocal()) and commits on its own.

request session  ──open──[ lookup ▸ INSERT user ▸ COMMIT ▸ SELECT last 20 ]──closed──▶
stream session                                    (later) ──open──[ INSERT assistant ▸ COMMIT ]──closed

Guardrails: what is refused, what is masked, and where

Phase 16 puts checks at every point where sensitive data can cross the boundary. The check always runs before the first database write, so a refused message leaves no trace, and a masked one is stored only in its masked form. These flows show each case end to end. The detail is in AI-Chat-Guardrails-Guide.html.

Where each check runs

Message inAfter validation, before the first insertRefused: 422, nothing storedMasked, then stored

Honest limit: these are pattern checks. They catch well-known key formats and checksummed numbers; they do not catch names or addresses, and they are a safety net, not a guarantee.

The end-to-end rig (used while building)

  1. A tiny local server speaks the OpenAI streaming format, with scripted behaviors: a normal reply, a slow reply, a connection that dies mid-stream, a 401, and a reply that leaks a fake key (to test the output guard).
  2. The real backend runs against it by setting OPENAI_BASE_URL, with a fresh SQLite file.
  3. A headless browser drives the real UI: streaming, Stop, refresh restore, retry without duplicates, delete, mobile drawer.

This is why the Phase 10 and 11 behavior was verified without spending real tokens.
