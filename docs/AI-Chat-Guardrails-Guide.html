AI Chat App: Guardrails

Guardrails: keeping secrets and personal data out, end to end

Phase 16 adds checks around the model so that API keys, passwords and personal data are refused or masked before they are stored or sent to the provider, and masked again if the model repeats them. Everything is a pattern check (regular expressions plus checksums): a safety net that prevents accidents, not a guarantee.

Why checksums matter

  • A card is only flagged if it passes the Luhn check, so a 16-digit order number usually isn't. An IBAN must pass its mod-97 check. An SSN can't use impossible areas such as 000 or 666.
  • A phone number needs 10 to 15 digits and a separator or a leading +, and an ISO date like 2026-10-30 is excluded.
  • password: something is prose; password: hunter2xx is a credential. A plain word is not flagged, a value with a digit or symbol is.

Messages in: refuse a secret, mask personal data

The check runs in the route before the message is stored, so a refused message leaves no trace and a masked one is saved only in its masked form. Follow each case.

Replies out: masking while the text streams

A model can repeat a secret it was shown (in a document, say) or invent something that looks like one. Replies are masked on the way out. The hard part is streaming: a key can be cut in half by the chunk boundary, so "sk-proj-abc" arrives first and "def…" later.

How StreamRedactor handles it

  1. Append each chunk to a buffer. If the buffer is no longer than 96 characters, emit nothing yet.
  2. Find matches in the whole buffer. Emit everything except the last 96 characters, masked.
  3. If a match starts before that cut and ends after it, move the cut to the match's end so it is never emitted half-masked.
  4. A private key whose END line hasn't arrived runs to the end of the buffer, so the whole unfinished block is held back until it completes (or the stream ends).
  5. At the end, flush the rest (masked). If the stream fails midway, flush too, so the saved partial reply is complete. If the client stops, nothing more can be sent.

Cost: text appears up to about 96 characters late, and short replies arrive in one piece. That is the price of never leaking half a key.

Uploads: before chunking, before embedding

Documents are the other way sensitive data gets in. The check runs on the extracted text, so masked data is never chunked, embedded or stored, and a masked email can't surface later in an answer.

What this does not do

Not coveredWhy it mattersWhat would help
Names, addresses, dates of birth, free-text identifiersNo pattern identifies them reliablyAn NER model (for example Presidio) with a measured false-positive rate
Unfamiliar secret formats, or secrets split or encoded by the userOnly known prefixes and shapes are matchedEntropy checks; a secrets scanner with a larger rule set
Prompt injectionThe warning on uploads is a weak signal; a model can still be influenced by text it readsKeep the model tool-less and secret-free (the real defense); evaluate with adversarial tests
Authentication and per-user dataRate limits are per address, and anyone who can reach the API can read every conversationUser accounts and ownership checks (required before a public deployment)
Rate limits across several workersCounts live in each processA shared store such as Redis, or limits at the proxy
Data already sent to the providerMasking only protects what passes through this server from now onThe provider's own retention settings and agreements
Trade-off to know: masking is lossy on purpose. A masked email can't be searched for or answered about, and a false positive (a long number that happens to pass a checksum) is masked too. Tune with GUARDRAIL_PII=off or block if that doesn't suit your data.
