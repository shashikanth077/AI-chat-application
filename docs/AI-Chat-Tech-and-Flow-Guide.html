1. System overview

AI Chat is a full-stack chat application. A React and TypeScript interface streams answers from a FastAPI backend. The backend calls an OpenAI-compatible model through LangChain. Conversations and uploaded documents are stored in SQLite. Answers can be grounded in the user's documents and cite them. Document vectors can optionally live in Qdrant. A separate, fully simulated demo runs on GitHub Pages with no server.

Browser

State and orchestration in App.tsx. Talks to the API with fetch and reads the SSE stream.

Backend

Routes validate input, run the guardrails, do the retrieval and stream the reply. Saves what was shown.

Data and providers

SQLite is the source of truth. Qdrant, the model and the embedder are replaceable parts behind small interfaces.

Why these choices

  • FastAPI + Pydantic: typed validation at the boundary; the route never runs with bad input.
  • SSE, not WebSockets: one-way token streams over plain HTTP; the browser's built-in reader is enough.
  • SQLite first: one file, no server, transactional, and fast enough for a single application. PostgreSQL is a configuration change later.
  • LangChain where it adds a standard interface: the model, the chain, the retrievers and the vector store. Chunking, the prompt escaping and the citations stay in our code, because they are security- and demo-critical.
  • Qdrant as an option, not a requirement: it adds a service. The default keeps the application runnable with no extra infrastructure.
  • Vitest and pytest: the tests run without keys or network, so CI is deterministic.

5.1 Startup: from 'run it' to 'chats on screen'

The backend boots without an AI key or a model client; the browser restores the last chat from the API.

  1. 1
    Developer → FastAPI (main.py): uvicorn main:app

    Uvicorn imports main.py. The module runs top to bottom, so the environment is read first.

    backend/main.py
  2. 2
    FastAPI (main.py) → FastAPI (main.py): load_dotenv + log filter

    backend/.env is loaded before any project import that reads the environment. The log filter that masks secrets is installed.

    main.py, guardrails/hardening.py
  3. 3
    FastAPI (main.py) → FastAPI (main.py): middleware + routers

    Security headers and the 2.5 MB body cap wrap everything. CORS allows CORS_ORIGINS (default localhost:5173). Routers are attached. The chat model is not created yet, so no key is needed to boot.

    main.py, services/llm.py
  4. 4
    FastAPI (main.py) → SQLite: lifespan: create tables

    init_db() runs create_all. First start creates the tables; later starts change nothing.

    database.py
  5. 5
    FastAPI (main.py) → Developer: Listening on :8000

    The server accepts requests. /health works with no key configured.

    main.py
  6. 6
    React (browser) → FastAPI (main.py): GET /conversations, /info, /documents

    The page loads. The UI asks for the chat list, the deployment facts (model, provider host, guardrail policy, vector store) and the document list.

    App.tsx, services/*
  7. 7
    FastAPI (main.py) → SQLite: SELECT conversations, documents

    Newest 100 conversations and all documents, read from SQLite.

    routers/*
  8. 8
    FastAPI (main.py) → React (browser): JSON

    The About dialog and the model chip use /info. It never contains a key.

    schemas.py: InfoResponse
  9. 9
    React (browser) → FastAPI (main.py): GET /conversations/{id}

    The active chat id is read from localStorage, so a refresh reopens the same chat.

    App.tsx: readStored(ACTIVE_KEY)

5.2 Send a message with documents (RAG, streamed, guarded)

The longest path: rate limit, guardrails, storage, follow-up rewrite, retrieval, citations, streaming, masking on the way out, and saving.

  1. 1
    React → FastAPI: POST …/messages/stream

    Body is only the new text, a client_message_id and the documents switch. The message rate limit runs before the handler (429 with Retry-After when exceeded).

    routers/conversations.py
  2. 2
    FastAPI → FastAPI: validate (Pydantic)

    1 to 4000 characters, not blank; the id is 8 to 64 characters. Failure is 422 and nothing runs.

    schemas.py
  3. 3
    FastAPI → Guardrails: check_input(text)

    A secret is refused: 422 with X-Guardrail: blocked, nothing stored. Personal data is masked to [REDACTED:EMAIL] and the masked text is what gets stored.

    guardrails/checks.py
  4. 4
    FastAPI → SQLite: INSERT user message (masked)

    Once per client_message_id. The title is set from the first message. Committed before the model is called, so Retry is safe.

    routers/conversations.py
  5. 5
    FastAPI → SQLite: SELECT last 20 messages

    The server decides the context from its own rows. A client cannot inject turns.

    _recent_context
  6. 6
    FastAPI → Model (LangChain): rewrite follow-up (documents on)

    A follow-up such as 'and how long do they nap?' becomes a standalone search query. One small call, used only for searching.

    services/rewrite.py
  7. 7
    Model (LangChain) → FastAPI: standalone query

    Length-checked (500 characters). Any failure falls back to the original question.

    rewrite.py
  8. 8
    FastAPI → Vector index: embed query, search (top 4)

    Embedding with fastembed (bge-small) or the offline hashing embedder. SQLite brute force, or Qdrant (which fetches 12 candidates, drops points whose document is not stored, then keeps 4). One LangChain retriever either way; the score threshold applies last.

    services/vectorstore.py, retriever.py
  9. 9
    Vector index → FastAPI: passages + scores

    Best first. Each passage carries document id, filename, position and score.

    services/retriever.py
  10. 10
    FastAPI → React: event: guardrail, event: sources

    Sent before any text. The bubble shows the masked text if anything was masked, and the citation chips appear.

    streaming.py
  11. 11
    FastAPI → Model (LangChain): chain.stream(system + <sources> + history)

    ChatPromptTemplate | ChatOpenAI | StrOutputParser. The server's system prompt, escaped sources in the last user turn, max 800 tokens, 30 s timeout. The first piece is awaited before the response starts, so an auth or rate-limit failure is still a real HTTP status.

    services/llm.py
  12. 12
    Model (LangChain) → FastAPI: tokens

    Text pieces stream back as the model writes them.

    _text_pieces
  13. 13
    FastAPI → Guardrails: guard_stream: mask output

    Secrets and personal data the model repeats are masked. The last 96 characters are held back so a split secret is still caught.

    guardrails/checks.py
  14. 14
    FastAPI → React: data: {delta} … event: done

    Each masked piece is an SSE frame. The first frame creates the bubble. done marks completion.

    streaming.py, services/sse.ts
  15. 15
    FastAPI → SQLite: INSERT assistant (masked) + sources

    Saved in a new session when the stream ends, is stopped or fails. The citation snapshot is copied, so it survives a document delete.

    routers/conversations.py

5.3 Upload and index a document

Text is checked, masked, chunked and embedded before anything is stored. The index is written before the SQLite commit.

  1. 1
    React → FastAPI: POST /documents (multipart)

    Client checks the type (.txt, .md, .pdf) and size first. Server enforces the same limits: 2 MB, 50 documents.

    routers/documents.py
  2. 2
    FastAPI → FastAPI: extract text (in memory)

    UTF-8 for text and markdown; pypdf for PDF. Nothing is written to disk.

    services/documents.py
  3. 3
    FastAPI → Guardrails: check_document(text)

    A secret refuses the whole file (422). Personal data is masked before chunking. Instruction-like phrases add a warning only.

    guardrails/checks.py
  4. 4
    FastAPI → FastAPI: chunk 800 chars, 100 overlap

    Paragraph-aware packing; at most 400 chunks per document.

    services/chunking.py
  5. 5
    FastAPI → Embedder: embed_documents(chunks)

    Unit-length vectors (384 floats for bge-small). The first call may download the model once.

    services/embeddings.py
  6. 6
    FastAPI → Vector index: write points (Qdrant only)

    Deterministic point ids. One collection per embedding model. SQLite backend: no-op, because the rows are written in the same transaction.

    services/vectorstore.py, qdrant_store.py
  7. 7
    FastAPI → SQLite: INSERT document + chunks

    Chunk text and the vector bytes are stored together, then committed.

    models.py
  8. 8
    SQLite → FastAPI: commit failed?

    If the commit fails, the new points are deleted again (best effort). Search also ignores any leftover points.

    routers/documents.py
  9. 9
    FastAPI → React: 201 {id, chunk_count, redacted, warnings}

    The panel says what was masked, and any warnings. Only the upload response carries those notes.

    schemas.py

5.4 Stop, failures and Retry

Stop keeps the partial answer and closes the provider connection. A failure before the first token is a real HTTP error. Retry re-sends the same id, so nothing is duplicated.

  1. 1
    React → FastAPI: stream open

    Tokens are arriving and the bubble grows.

    App.tsx: requestReply
  2. 2
    Model provider → FastAPI: tokens

    Pieces stream in.

    llm.py
  3. 3
    React → FastAPI: Stop: connection closed

    AbortError is recognised; it is not an error. Starlette raises GeneratorExit in the response generator.

    streaming.py
  4. 4
    FastAPI → Model provider: close upstream stream

    The guard's finally closes the chain's stream, which closes the HTTP connection. No more tokens are generated or billed for text nobody will read.

    guardrails/checks.py
  5. 5
    FastAPI → SQLite: save partial (masked)

    The masked partial text is stored in a new session. A refresh shows exactly what was on screen.

    streaming.py finally
  6. 6
    React → FastAPI: Retry: same client_message_id

    Failure before the first token: the status is real (504, 502, 429 or 500) and the UI shows an error with Retry.

    services/llm.py: _translate
  7. 7
    FastAPI → SQLite: find id → delete later rows

    The stored user message is found, so no second copy. Whatever followed it (the partial answer) is deleted.

    routers/conversations.py
  8. 8
    FastAPI → React: fresh streamed answer

    Exactly one user message and one answer afterwards.

    test_conversations.py

5.5 Delete a conversation or a document

SQLite is committed first; index entries are removed afterwards and are never returned even if that step fails.

  1. 1
    React → React: confirm dialog

    Accessible modal (focus trap, Escape). Nothing is sent until the user confirms.

    components/ConfirmDialog.tsx
  2. 2
    React → FastAPI: DELETE /conversations/{id}

    Also used by the cleanup of a chat created by a refused message.

    routers/conversations.py
  3. 3
    FastAPI → SQLite: DELETE (cascade)

    Messages and their citation snapshots go with the chat, by ORM cascade and by foreign key.

    models.py
  4. 4
    FastAPI → React: 204 No Content

    The list refreshes. Other chats are untouched.

    App.tsx
  5. 5
    React → FastAPI: DELETE /documents/{id}

    Deleting a document removes its chunks in SQLite.

    routers/documents.py
  6. 6
    FastAPI → SQLite: commit document delete

    The source of truth changes first.

    routers/documents.py
  7. 7
    FastAPI → Vector index: delete points (best effort)

    If this fails the response is still 204. Search hides the leftovers; reindex_qdrant.py --prune removes them.

    services/vectorstore.py

5.6 Demo mode: the same app with no server

The public GitHub Pages build answers its own API calls in the browser, with simulated replies and no key, no shared database and no backend.

  1. 1
    Visitor → GitHub Pages: open the project link

    A static build of the frontend is served. Nothing dynamic runs on GitHub's side.

    deploy-demo.yml
  2. 2
    GitHub Pages → React (VITE_DEMO): index.html + JS bundle

    Built with VITE_DEMO=true and VITE_BASE set to the repository path.

    vite.config.ts
  3. 3
    React (VITE_DEMO) → Demo API (browser): fetchOrThrow → demoFetch

    The same services and SSE parser run. Only the transport is swapped (dynamic import, so the demo code is not in the main bundle).

    services/http.ts
  4. 4
    Demo API (browser) → localStorage: read/write chats and uploads

    All state is in this browser. Nothing is sent to a server.

    demo/store.ts
  5. 5
    Demo API (browser) → Demo API (browser): guardrails (TypeScript port)

    Refuses secrets and masks personal data, tested against the Python detectors on a shared fixture.

    demo/guardrails.ts
  6. 6
    Demo API (browser) → Demo API (browser): retrieve + simulated reply

    Client-side RAG: the chunking and hashing embedder are ports, tested for parity. The answer is composed from the passages and streamed word by word.

    demo/rag.ts, assistant.ts
  7. 7
    Demo API (browser) → React (VITE_DEMO): SSE frames: sources, guardrail, delta, done

    Streamed exactly like the real server, so the UI code path is the same.

    demo/api.ts

6. Security and guardrails

Defence in layers. Each layer stops one class of problem, and none is treated as complete on its own.

ConcernControlWhere
Secrets typed or pastedRefused with 422; the text returns to the box; nothing stored or sentguardrails/checks.py
Personal data typed or uploadedMasked before storing, chunking and embeddingguardrails/checks.py, routers/documents.py
Secrets or personal data in a replyMasked while streaming; the saved reply is the masked oneguardrails/checks.py: guard_stream

7. Deployment

Two targets. The demo is safe to publish because it has nothing to protect. The full stack holds a key and user data and is run by you, behind TLS, with the settings below.

Full-stack checklist

  1. Set OPENAI_API_KEY and OPENAI_MODEL in the server's environment, never in the frontend build.
  2. Set CORS_ORIGINS to the exact frontend origin.
  3. If Qdrant: set QDRANT_API_KEY, run docker compose up -d qdrant, set VECTOR_STORE=qdrant and QDRANT_URL, then run tools/reindex_qdrant.py --prune.
  4. Keep the database and the Qdrant volume on persistent disks; back up both.
  5. Set TRUST_PROXY=true only if your own proxy overwrites X-Forwarded-For.
  6. Run the smoke test against the deployed site before announcing it.

11. Limits and verification status

What this guide and the test suite establish, and what they do not. Read this before relying on a claim above.

  • Detection is patterns and checksums. Names, addresses and unfamiliar secret formats are not caught.
  • Authentication is not built. Anyone who can reach the API can read every conversation. Required before any public deployment.
  • Rate limits are per client address and per process. Several workers each keep their own count.
  • Qdrant server mode has not been run in this project's environment (no Docker daemon). The embedded and in-memory modes are tested.
  • The default embedder (bge-small) has not been measured here: model download is blocked in the build environment. The threshold of 0.5 is a starting point.
  • Follow-up rewriting is tested with a scripted model. Its quality with a real model is unmeasured.
  • The GitHub Actions workflows have not run on GitHub from this environment. They are validated as YAML and locally by their commands.
  • The demo build is simulated: it has no real model and no output guard on a real reply.
