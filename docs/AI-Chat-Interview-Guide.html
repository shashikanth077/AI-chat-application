Phase 1: Project setup

Q1.1 Why must the OpenAI call go through a backend instead of the browser?

Anything in browser code is public. Anyone can open devtools or read the bundle and copy the key, then run up your bill. The backend holds the key in an environment variable, and the browser only calls your own API.

Q1.2 What is a Python virtual environment, and what is the Node equivalent?

A virtual environment is an isolated Python install with its own packages, so projects don't collide. It's like a local node_modules, but it also holds its own interpreter. Without one, pip installs globally.

Q1.3 What does `uvicorn main:app` mean; how do FastAPI and Uvicorn relate?

It means: in module main.py, use the object named app. FastAPI is the framework that defines routes and builds the app. Uvicorn is the ASGI server that listens on a port and runs it. Like Express (framework) and Node's http server (runtime).

Phase 2: React UI with mocks

Q2.1 Why compute the new array first instead of calling setMessages then reading messages?

State updates are asynchronous and batched. Reading messages right after setMessages still gives the old array. Building history = [...messages, userMsg] first gives a value you can use immediately, both for the UI and for the API call.

Q2.2 Why separate chatService.ts from the components?

Components only render and emit events. The service owns the network. Swapping the mock for a real fetch touched one file, and no component changed.

Q2.3 How do you prevent a double submit while a request is in flight?

Two guards: the button is disabled while loading (the disabled prop), and submit() re-checks canSend, so pressing Enter can't bypass the button. A state flag is the source of truth, not the DOM.

Phase 3: Hardcoded endpoint

Q3.1 Why does GET /chat return 405 instead of 404?

405 means the path exists but this method isn't allowed for it. 404 means no route matches the path at all. FastAPI knows /chat exists as a POST route, so it reports the method mismatch.

Q3.2 When would you use def vs async def in FastAPI?

A def route runs in a thread pool, which suits blocking work like the synchronous OpenAI client. async def runs on the event loop and must never call blocking code, because that freezes every request. Use async def only with async clients.

Q3.3 How does FastAPI generate /docs without documentation code?

It reads the route decorators and type hints (including Pydantic models), builds an OpenAPI schema, and serves Swagger UI on top of it. The code is the documentation.

Phase 4: Pydantic validation

Q4.1 How does a JSON body become a Python object in FastAPI?

FastAPI reads the body and parses the JSON into a dict. Because the parameter is typed as a Pydantic model, it validates and converts the dict into a ChatRequest instance. Invalid data returns 422 with field-level errors, and the handler never runs.

Q4.2 Why validate on the backend when the frontend already validates?

Frontend checks are for user experience. Anyone can call the API with curl and skip the UI. The server is the only enforcement point, and it protects both cost and data quality.

Q4.3 Why Literal["user","assistant"] for role, and why reject "system"?

Literal limits the field to exact values, like a TypeScript union of string literals. Rejecting system stops a client from injecting instructions. The server owns the system prompt, so clients can't override it.

Phase 5: Fetch and CORS

Q5.1 What is CORS, who enforces it, and what is a preflight request?

CORS (Cross-Origin Resource Sharing) is a rule the browser enforces. A page on one origin can read a response from another origin only if that server allows it in its headers. A preflight is an OPTIONS request the browser sends first for non-simple requests, such as JSON POSTs. curl and servers aren't bound by CORS.

Q5.2 Why does fetch not reject on HTTP 4xx/5xx, and how do you handle that?

fetch only rejects on network failure. An HTTP error is still a valid response. Check response.ok, read the body (FastAPI puts errors in detail), and throw an Error with a readable message.

Q5.3 Why not allow_origins=["*"], and how would you configure this for production?

A wildcard lets any website's JavaScript call your API from a visitor's browser. Use an exact list of HTTPS origins, from an environment variable. CORS isn't authentication, so add auth before opening the API to real users.

Phase 6: OpenAI integration

Q6.1 Why keep the API key on the server, and how do env vars, .env and .gitignore work together?

.env holds the key on your machine. load_dotenv() loads it into the process environment, and .gitignore keeps the file out of commits. The browser never sees it. In production, the platform's secret store replaces .env. Vite's VITE_ prefix is public, so secrets never use it.

Q6.2 What is a system prompt versus user/assistant messages, and why must the server own it?

The system prompt sets the assistant's rules and behavior. User and assistant messages are the conversation. The server owns the system prompt so clients can't change the rules. Prompt injection can still affect a model, so the system prompt isn't a security boundary by itself.

Q6.3 How do you handle OpenAI failures without leaking internals, and which status codes do you map them to?

Catch specific SDK exceptions and map each to a status and safe message: timeout 504, connection 502, rate limit 429, bad key or missing config 500, other provider errors 502. Log the details on the server only. The order matters, because APITimeoutError is a subclass of APIConnectionError.

Phase 7: History, limits and retry

Q7.1 Why trim conversation history before sending, and what are the trade-offs?

Each turn re-sends the whole history, so cost and latency grow, and providers have context limits. A sliding window of 20 bounds both. The trade-off is that the model forgets older turns. Summaries or retrieval (RAG) are the usual next step.

Q7.2 Why does the chat UI keep the user message after a failed request, and how does Retry avoid duplicates?

The user's input is valid and shouldn't be lost. In Phase 7, Retry re-sent the messages already in state, so nothing was appended twice. Phase 11 made this server-side and idempotent: every message carries an id, and re-sending the same id replaces the answer instead of duplicating the message (see question 11.2).

Q7.3 Why must input limits exist on both frontend and backend, and which one is the real security boundary?

The frontend limit is for honest users and gives immediate feedback. The backend limit is the boundary, because any client can bypass the UI. Keep the two constants in sync.

Phase 8: Testing and provider flexibility

Q8.1 How do you unit-test code that calls an external API, and what should and should not be mocked?

Mock the external boundary (the SDK client or HTTP layer) and run your own code for real. Test validation, error mapping and CORS through the real app with TestClient. Assert that invalid input never calls the mock. Don't mock the logic under test, or the test proves nothing. Keep a few real-provider checks for manual testing.

Q8.2 Why use the Chat Completions format with a configurable base URL, and what does that buy you?

Chat Completions is the most widely implemented format, and many providers (Groq and others) implement it. Changing base_url and the model in config switches providers with no code change. The trade-off is that newer API features may not be available everywhere.

Q8.3 How would you debug a request that works in Swagger but fails in the browser?

Swagger and curl bypass CORS, so suspect CORS first: check the preflight and the allow-origin header in devtools. Then compare the exact request: Content-Type, body, and URL, including the port. Check that the frontend uses the right API URL, and check the server log for the real error.

Phase 9: Project-level questions

Q9.1 Explain the whole architecture end to end in two minutes.

The React UI sends only the new message (plus an id) to POST /conversations/{id}/messages/stream. FastAPI validates it with Pydantic, stores it in SQLite, and loads the last 20 stored messages as context. If the user turned documents on, it embeds the question, finds the best passages, and puts them in a delimited block in the user turn. It calls an OpenAI-compatible model with a server-owned system prompt and streams the reply back as Server-Sent Events, sources first. The answer and its citations are saved when the stream ends. Errors map to safe HTTP codes, and the API key never leaves the server.

Q9.2 How would you deploy this to production?

Put the backend on a host with secret management and no .env file. Move from SQLite to PostgreSQL and add migrations (Alembic). Serve the built frontend from a CDN or the same domain. Restrict CORS to the real origin, add authentication, per-user ownership of conversations and documents, request-size limits at the proxy, and per-user rate limits. Add logging, monitoring, backups, and an evaluation set for retrieval quality.

Q9.3 What are the biggest gaps or risks in this app today, and how would you close them?

No authentication, so every conversation and document is readable by anyone who reaches the API: add accounts and ownership checks. Prompt injection through documents is reduced but not solved: add least privilege, no tools or secrets for the model, and vetting of sources. Retrieval is brute force and only searches the newest message: add an index for scale and query rewriting for follow-ups. The relevance threshold is an unmeasured default: build a small labeled set and tune it. Concurrent sends to one conversation aren't locked.

Phase 10: Streaming

Q10.1 Why use Server-Sent Events instead of WebSockets for streaming a chat reply, and when would you pick WebSockets?

A chat reply only flows server to client, and SSE is exactly that over plain HTTP: it needs no special protocol, works with ordinary proxies and auth headers, and each frame is a simple text block. The user's message is a normal POST. WebSockets are bidirectional and persistent, so they fit collaborative editing, games, live cursors, or streaming audio from the client, at the cost of stateful connections that are harder to load-balance and secure. Here we read the stream with fetch and a stream reader, because the browser's EventSource can't send a POST body.

Q10.2 Once a streaming response has started with HTTP 200, how do you report a later failure, and what should the client do if the stream ends without a done event?

The status line is already sent and can't change, so the failure travels inside the stream as an event: error frame with a safe message. The client throws, keeps the partial text, and offers Retry. A cut connection looks like a normal end of the body, so the client also treats any stream that ends without a done frame as interrupted. Failures before the first token are still real HTTP errors, because the provider call is opened before the response object is returned.

Q10.3 What happens when the user clicks Stop or closes the tab, and how do you make sure the server stops paying for tokens nobody will read?

The client aborts the request with an AbortController, which closes the connection. The server detects the disconnect and closes the response generator, which raises GeneratorExit at its yield. The finally block then closes the upstream stream, so generation stops, and saves the partial text. Closing the tab does the same server-side steps. Tokens generated before the provider notices the closed connection may still be billed, so Stop bounds the cost without making it zero.

Phase 11: Persistence

Q11.1 Why should the server, not the client, own the conversation history, and what attacks or bugs does that prevent?

If the client sends the history, a modified client can forge assistant or system turns to steer the model, inflate the prompt to raise cost, or send history that disagrees with other tabs and devices. With server-owned history the client sends only the new text, the server builds context from rows it wrote itself, and there is one source of truth that survives refreshes. It is only fully safe once authentication ties each conversation to its owner.

Q11.2 How does sending a client-generated message id make retry safe (idempotent), and what would go wrong with a naive retry that just re-posts the message?

Each user message carries a UUID, and a unique constraint on (conversation, client id) stops it being stored twice. Re-sending the same id means retry: the server deletes whatever followed that message, such as a partial answer, and regenerates. A naive re-post would store the message twice, leaving duplicate context and cost. A naive regenerate-last-answer endpoint would be worse: if the original send never reached the server, it would delete the previous, complete answer. With ids, a message that never arrived is simply new, and nothing is deleted.

Q11.3 Why SQLite for development with SQLAlchemy, what changes when you move to PostgreSQL, and what is missing before you could deploy this?

SQLite needs no server, and SQLAlchemy keeps the code portable, so moving to PostgreSQL is mostly a connection URL and a driver. Differences to handle: SQLite needs foreign keys switched on explicitly and allows a single writer, while PostgreSQL enforces keys and scales writes. create_all never alters existing tables, so schema changes need migrations (Alembic). Before deploying you also need authentication and ownership checks, rate limits, backups, locking for concurrent sends, and tight CORS.

Phase 12: Documents and retrieval

Q12.1 What is RAG and why does it exist? What problem does it solve that a bigger prompt or fine-tuning does not?

Retrieval-augmented generation fetches the most relevant text from your own data at question time and puts it in the prompt, so the model answers from it. It gives the model knowledge past its training cutoff or from private data, grounds answers so they can cite sources, and updates the moment a document changes. Stuffing everything into a prompt hits context limits and cost, and long contexts degrade. Fine-tuning mainly changes style and behaviour, not reliable facts, is costly to refresh, gives no citations, and makes removing data hard.

Q12.2 How does chunking affect retrieval quality? Explain the trade-offs of chunk size and overlap.

Chunks that are too large blur many ideas into one vector, so matches are vague and the prompt wastes tokens. Chunks that are too small lose the surrounding context and return fragments. Overlap keeps an idea that straddles a boundary intact in at least one chunk, at the cost of extra storage and near-duplicate results. This app packs paragraphs up to 800 characters (about 200 tokens) with 100 characters of overlap inside long paragraphs. A test found a real bug: the overlap silently disappeared because pieces already filled the size limit, so long paragraphs are now cut a little shorter to leave room.

Q12.3 What is an embedding, why do we normalize vectors, and why is cosine similarity then just a dot product?

An embedding is a list of numbers (384 here) that places a piece of text in a space where similar meanings are close. Cosine similarity compares direction, a.b / (|a||b|). If every vector is scaled to length 1, the denominator is 1, so similarity is just the dot product. Scoring every stored chunk then becomes one matrix-vector multiplication, which is fast.

Q12.4 Why does top-k search always return k results even when nothing is relevant, and how do you handle that?

Nearest-neighbour search ranks whatever exists, so the closest items are returned however far away they are. The fix is a relevance threshold: ignore passages scoring below a cut-off, and tell the model when nothing qualified. The cut-off depends on the embedding model, so it must be measured with queries that should and should not match. Phase 13 implements it.

Q12.5 Why must documents be re-embedded if you change the embedding model, and how does this app protect against mixing them?

Different models place text in different spaces, often with different dimensions, so scores across models are meaningless. This app records which model produced each document's vectors and searches only documents embedded with the current model. Others are simply ignored until re-uploaded. A larger system would re-embed in the background instead.

Phase 13: RAG in the chat

Q13.1 Walk through what happens, step by step, when a user asks a question with RAG enabled. Where can quality be lost?

The message is saved, then the question is embedded and compared with every stored chunk; the best 4 above the threshold go into a delimited sources block in the user turn, with rules in the system prompt. The model streams an answer citing [n]; the sources frame is sent first, and the answer plus a snapshot of the passages is saved. Quality can be lost at every stage: chunking that splits an answer, an embedding that misses vocabulary or a follow-up with no context, a threshold set too high or too low, the top-k cut-off, the model ignoring or misusing the sources, or citing a number it never used.

Q13.2 What is prompt injection, why is retrieved text especially exposed to it, and what did this app do and not do about it?

Prompt injection is text that tries to override the model's instructions. Retrieved documents are untrusted input that gets pasted into the prompt, so an uploaded file can carry instructions (indirect injection). Here, passages go in the user turn inside a delimited block, never the system prompt; any sources tags inside them are escaped so a document can't close the block; the system prompt says to treat the block as reference text and never follow instructions in it; and the model has no tools or secrets to misuse. This lowers the risk but can't remove it, since a model may still be influenced by what it reads. Not done: output filtering, scanning documents, or per-user document libraries.

Q13.3 How do you choose a relevance threshold, and what goes wrong when it is too low or too high? How would you evaluate retrieval quality properly?

Measure it: collect queries that the documents should answer and queries they should not, look at the score distributions, and pick a value that separates them, trading precision against recall. Too low and unrelated passages reach the model, which then answers confidently with misleading citations. Too high and real matches are dropped, so the answer says nothing was found. Scores differ per model, so re-tune after any model change. Proper evaluation uses a labeled question set with metrics such as recall@k and MRR for retrieval, plus checks that answers are faithful to the sources. This app's 0.5 default is an unmeasured guess, which the docs say plainly; citations show scores so you can calibrate.

Q13.4 Why store citations as a snapshot instead of a reference to the document, and what are the trade-offs?

A reference can dangle or point at changed text if the document is edited, re-chunked or deleted, so the citation would no longer show what the answer actually relied on. A snapshot copies the passage, filename and score with the answer, so it stays accurate and needs no new migration. The trade-offs are duplicated storage, text that may be stale compared with the current document, and a privacy catch: deleting a document does not erase its text from old citations, only deleting the conversation does.

Q13.5 Why does a follow-up like "what about its price?" retrieve poorly, and how would you fix it?

Only the newest message is embedded, and "its" has no meaning without the earlier turns, so the vector matches nothing in particular. Fixes: ask an LLM to rewrite the question as a standalone one using the chat history before searching, embed the last few user turns together, or combine vector search with keyword search. Each adds an extra model call or complexity, so measure whether it pays off.
